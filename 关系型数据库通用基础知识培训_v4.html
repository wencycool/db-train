第一章 · 从零开始

数据库、实例与 Schema
——三个你必须分清的概念

很多人混用这三个词，但它们描述的是完全不同的层面。理解它们的区别，是所有运维工作的起点。

类比思路

把数据库系统想象成一栋写字楼：数据库（Database）是这栋楼本身，实例（Instance）是楼房物业（负责开门、管理、调配资源），Schema是某一层楼的格局和房间编排。

  • DB

    数据库（Database）

    物理上存储在磁盘的一组文件集合：数据文件、控制文件、日志文件。它是静态的——即使系统关机，数据仍在磁盘上持久存在。

  • INS

    实例（Instance）

    数据库在内存中的"活体"：一组后台进程（进程池）+ 共享内存结构（SGA/Buffer Pool）。实例是动态的，重启后重新创建。Oracle 可以多个实例共享一个数据库（RAC），MySQL 则是一对一。

  • SCH

    Schema（模式）

    数据库内的逻辑命名空间，相当于"用户名下的所有对象集合"。在 Oracle 中 Schema = 用户；在 PostgreSQL 中一个数据库可以有多个 Schema；在 MySQL 中 Schema 约等于 Database。

第二章 · 数据的家园

表与表空间
——数据住在哪里？

表（Table）是关系型数据库最基本的存储单元；表空间（Tablespace）则是管理这些表物理存储的"地皮"概念。

📋 表（Table）是什么？

表是按行（Row）和列（Column）组织数据的二维结构。每一列有固定的数据类型（整数、字符串、日期……），每一行代表一条真实的业务记录。

在磁盘上，表的数据被切成固定大小的页（Page/Block），Oracle 默认 8KB，PostgreSQL 默认 8KB，MySQL InnoDB 默认 16KB。所有 I/O 操作都以页为最小单位。

运维重点

表的物理增长会导致空间不足告警。定期监控表空间使用率是运维日常。当表极大时，还需关注分区表（Partitioned Table）——按时间或范围切成多个子分区，方便管理。

🏗 表空间（Tablespace）是什么？

表空间是逻辑存储容器，它映射到磁盘上的一个或多个数据文件。你可以把表空间看作"逻辑硬盘分区"——数据库不直接操作文件路径，而是操作表空间名。

表空间 → 数据文件 → OS文件 映射关系

堆表 vs 索引组织表（IOT）

存储行数据的方式决定了查询效率——这是两种截然不同的物理组织策略。

实际案例

MySQL InnoDB 的主键即 IOT（聚簇索引），数据按主键顺序存储。这就是为什么 InnoDB 强烈建议使用自增整数主键——随机 UUID 会导致大量页分裂，严重影响写入性能。

第三章 · 查询加速器

索引（Index）
——为何查询快了100倍？

索引是数据库最重要的性能工具。理解它，就能看懂 80% 的性能问题。

生活类比

没有索引的查询就像在一本没有目录的字典里逐页找"数据库"——必须翻完所有页（全表扫描）。索引就是那本目录，让你直接跳到正确页码。

B+树索引的工作原理

绝大多数数据库（Oracle、MySQL、PostgreSQL、DB2）默认使用 B+树（B+ Tree）索引。它有三个关键特点：

  • 有序

    键值有序排列

    所有键值在树中有序存储，支持等值查找、范围查找、ORDER BY 优化。

  • 矮

    树高极低

    一亿行数据的 B+树高度通常只有 3-4 层，每次查找只需 3-4 次 I/O。

  • 链

    叶节点链表相连

    叶层形成双向链表，范围扫描无需回到根节点，连续读取效率极高。

B+树索引结构（查找 id=6）

B+Tree 访问路径：按场景切换理解

索引回表点查：WHERE user_id = 106

从 Root 判断数字区间，下降到对应 Branch，再进入包含目标 user_id 的 Leaf Page，最后按 ROWID 访问数据页。

定位成本树高通常很低，先通过根/分支页迅速定位叶页。
索引项内容二级索引叶子项通常保存 key + ROWID / 主键引用。
回表动作当查询列不全在索引里，就要再读数据页取得完整行。
索引范围扫描：WHERE user_id BETWEEN 106 AND 212

先定位范围下界所在叶页，然后沿叶页 next 指针顺序扫描，读到超过上界的 user_id 后停止。

起点定位范围扫描不是从第一片叶页开始，而是先找到下界 key。
叶页链表页头 prev/next 让相邻叶页可以顺序读取。
停止条件第一个超过上界的 user_id 出现时，扫描立即结束。
LIKE 扫描对比：LIKE 'abc%' vs LIKE '%abc'

B+Tree 按左前缀排序；LIKE 'abc%' 可以裁剪成局部范围扫描，LIKE '%abc' 只能做 Index Full Scan 后过滤。

左前缀组织索引项先按 name 的第一个字符排序，再比较后续字符。
前缀可裁剪abc% 能转成连续区间：从 abc 开始，到 abd 前停止。
后缀需过滤%abc 的候选分散在整棵叶层，常表现为 Index Full Scan 后再过滤。
运维注意

索引不是越多越好——每次 INSERT/UPDATE/DELETE 都要同步维护索引，索引过多会严重拖慢写入。业务高峰期前后需做索引审查（无效索引清理）。

「一个好的索引设计，胜过一百次 SQL 调优。」

第四章 · 速度的秘密

缓存（Buffer Cache）
——为什么内存那么重要？

磁盘 I/O 是数据库最大的性能瓶颈。缓存的使命，就是用内存的速度换掉磁盘的延迟。

图示 · 数据库内存结构全景（以通用结构为例）

缓存命中率（Buffer Hit Rate）

缓存命中率 = 从内存读取的页次数 ÷ 总读取页次数。这是衡量数据库内存是否充足的黄金指标。


命中率 99%+ ✅ 健康
命中率 95-99% ⚠️ 关注
命中率 <95% 🚨 扩内存

脏页（Dirty Page）与刷盘

当缓冲区的数据被修改后，该页成为脏页（内存数据与磁盘不一致）。后台进程（DBWriter / bgwriter）会定期将脏页刷回磁盘。

1

SQL 更新

UPDATE 语句修改 Buffer Cache 中的页，该页标记为 Dirty。

2

写 WAL/Redo 日志

修改记录先写入日志缓冲，再同步到磁盘日志文件（保证持久性）。

3

异步刷盘

后台进程择机将脏页写回数据文件。宕机时用日志重做（Redo）恢复。

第五章 · 数据的保险箱

日志与归档
——崩溃时数据怎么不丢？

日志是数据库最关键的安全机制。没有日志，任何一次意外都可能造成数据灾难。

为什么必须开启归档模式？

①

支持热备份

归档模式下可在不停库的情况下做在线备份（RMAN、xtrabackup），业务零中断。

②

支持 PITR（点位恢复）

可将数据库恢复到任意历史时间点，将数据丢失窗口从"上次全备"缩到"最后一个已归档日志"。

③

支持主从/灾备复制

备库通过传输和应用归档日志（或在线日志）保持与主库的实时同步。

数据库权限体系：从身份到数据

👤

用户（User / Account）

数据库登录主体。每个系统、应用、开发人员或运维人员通常对应独立账号，用于身份识别与权限隔离。

🎭

角色（Role） （基本不使用）

权限的集合。通过“角色 → 用户”的方式统一授权，例如 DBA、开发、只读查询角色，降低权限维护成本。

🛠️

系统权限（System Privilege）

对数据库系统级资源的操作权限，例如 CREATE USER、CREATE TABLE、ALTER DATABASE、CREATE SESSION。通常仅授予管理员角色。

📋

对象权限（Object Privilege）

针对具体数据库对象的权限，例如表、视图、存储过程。常见权限包括 SELECT、INSERT、UPDATE、DELETE、EXECUTE。

🧩

数据级权限（Data-Level Control） （不使用）

进一步限制“能看到哪些数据”，例如行级权限（Row-Level Security）、列级脱敏、按部门隔离数据。

🔐

安全原则（Security Principle）

遵循最小特权原则：应用账号仅授予必要权限；DBA、业务账号、审计只读账号相互隔离，避免高权限滥用。
